# Party Presents

A phone app for the children's party invitations: every party Charlie and Sophie are invited to in one shared calendar, a reminder in good time, and a clear record of who's getting the present, so it isn't a last-minute scramble and you never both buy one.

It's built the same way as [weekly-shop-app](https://github.com/andrewwilson201/weekly-shop-app): a static site (plain HTML, CSS and JavaScript, no build step) on Firebase Hosting at **https://kids-presents.web.app**, with Firebase Auth and Firestore in its own Firebase project (`kids-presents`, database in London), and a few Firebase functions for Claude and the reminders.

## How it works

- **Family**: the first person signs in with Google and makes the family's space. Settings › Share invite link sends a link; whoever opens it and signs in joins. Everything lives under `households/{id}` and only members can read or write it ([`firestore.rules`](firestore.rules)). Changes show on both phones straight away.
- **Children**: Charlie and Sophie to start with (Settings › Children: names, birthdays, add another). Each has a colour, used on their parties everywhere. A party is for one of them or both.
- **Parties**: the home screen lists what's coming up, each with whether a present is sorted (*1 needs a present · 1 being bought*). Add one by hand, or from an invite. Adding the same birthday child on the same day asks before making a second party.
- **Joint parties**: a party for more than one birthday child (twins, friends sharing) is one party with a present per birthday child. On the form, **Joint party? Add another birthday child**; an invite that names several is read that way too. The party's page has a tab per birthday child, each with their own ideas, who's getting it and bought state; lists show one row with each child's present. Underneath, it's one event per birthday child sharing a `groupId` and the party's details ([`js/gifts.js`](js/gifts.js) `siblingsOf`); reminders about a present are per child, the reply and morning-of reminders are sent once, and the calendar feed shows one entry. A party both Charlie and Sophie are invited to is *Who's invited: Charlie & Sophie*.
- **Invites**: on Android, once the app is installed (Chrome › Add to Home screen), open the invite in WhatsApp, tap Share and pick Party Presents. That works for a picture or for a message's words; you can also pick a picture from your photos, paste a copied one, or paste the message into *Read an invite*. A picture is made smaller and saved apart from its scan (`scanImages`), so opening the app doesn't download old pictures. The `readInvite` function has Claude read the birthday child's name and age, date, times, venue, address, reply-by date and contact, works out which of the children it's for, fills in what's known about that friend from earlier years, and adds the party marked *Read from an invite* so you can check it (**Looks right** or **Change details**). If that child's party is already in the calendar for that day (you both shared the invite), nothing is added twice: you're taken to the one that's there and any gaps in it are filled.
- **The present**: a party's page offers, in order, anything suitable in the cupboard, **Find real presents in the shops**, a few saved ideas that fit (budget, age, boy or girl, interests), and a box to type your own. The friend's age defaults to your child's age if the invite doesn't say. Tap **I'll get this** and the other person sees *Sarah is getting this*, with a link to the product or shop searches for it; then **Bought it** (where from, how much) and **Wrapped, with a card**. Claiming is a database transaction, so if you both tap at once only one wins and the other is told who has it (`claimPresent` in [`js/store.js`](js/store.js)). **I'll get it instead** takes over a claim that hasn't been bought yet. **Given to Olivia before** lists earlier presents to the same friend, and those ideas drop down the list. Cancelled, no present needed and delete are under **More**.
- **Real products**: **Find real presents in the shops** has Claude search UK shops' websites (the API's web search tool) for about six actual products within the budget, each with its price, shop and a link to the product page, saved on the party so you both see them (`findProducts` in [`functions/claude.mjs`](functions/claude.mjs)). It takes a minute or two and costs a few pence. Prices and stock are as found at the time, so check before buying. Links must be https and, where the search results can be checked, must be pages the search really returned. From a party's **More ideas**, an idea's **Find real ones in the shops** searches for that kind of thing.
- **The exact present**: for your own idea, paste the product's link from a shop into *Or something else* (or into the form when you mark a present bought). The `suggestIdeas` function reads the page ([`functions/link.mjs`](functions/link.mjs): the shop's own product details first, Claude's web fetch if the shop turns robots away) and fills in the name, price and picture, which you can correct. Only public https addresses are fetched. Everything marked bought is kept in the ideas as *Bought before*, with its link, age and interests from the party, so it's suggested for the next child it suits.
- **Ideas**: the ideas database starts with 118 researched starter ideas (`data/ideas.json`, made by [`tools/make-ideas.py`](tools/make-ideas.py): typical UK prices, age ranges, interests, search words). Filter by budget, boy or girl, age and interests; ideas that fit equally well are mixed by kind. **Ask Claude for ideas** gets 8 suggestions that mix your saved ideas with new ones; new ones are saved, marked *Claude*, so the database grows. Like the good ones, hide the duds, add your own. Each idea has links that search Amazon UK, Argos, Smyths and John Lewis.
- **Cupboard**: presents bought ahead (a sale, a multi-buy), beside Ideas under the same tab. A party's page offers the ones that suit it; using one marks the party's present as bought. An idea's **Bought one for the cupboard** adds it.
- **Friends**: everyone whose party has been in the calendar, per child, with what they're into, how old they are now and what you've given them. Nothing is typed in: it's worked out from the parties (`friendsFrom` in [`js/gifts.js`](js/gifts.js)), and a friend is their name plus which of your children they belong to, so two Jacks stay apart. When a friend's party was about this time in an earlier year and nothing is in the calendar yet, the home screen says *Tom turns 7 around 21 November* with **Add it** (the form starts from last time, a year older) or **Not this year**. Typing a known name on the form fills in the rest.
- **Reminders**: at 8am every day (`dailyReminders`), phones with notifications on (Settings › Notifications, each phone) get: *Present needed* 10 days before if nothing is bought, *Still need a present* 3 days before, a reply reminder 2 days before the reply-by date if you haven't marked Going or Can't go, and on the day *take the present and card*. The days are in Settings › Reminders. Each one is sent once per party (`reminded` on the party), and only counts as sent once it has reached a phone, so if nobody has notifications on yet it's tried again the next morning. The rules are `dueReminders` in [`js/gifts.js`](js/gifts.js).
- **Calendar**: a month view with a dot per party in each child's colour. Settings › Calendar › **Connect Google Calendar** (once, by one of you) puts every party still to come into that Google Calendar and invites the rest of the family, so it's in both your calendars; changes follow, and a cancelled party or one you're not going to is taken out ([`functions/gcal.mjs`](functions/gcal.mjs), the `calendarSync` function; the connection is kept in `calendarLinks/`, which only the functions can read). There's also a private calendar feed (`/calendar.ics`, served by the `calendar` function) to add to Google Calendar, so parties show in your phone's own calendar with the present's status in the notes.
- **Who can use it**: the address and repo are public, so anyone with a Google account can sign in, but they can't do anything. The first family can be made freely; that writes `config/access` (`{ households: [id] }`, by the `newHousehold` function), and after that new families can only be made while a `config/open` document exists. Claude, reminders and the calendar feed only serve families on that list. Only the admin key can read or write `config/`.

## One-time setup (done 16 Nov 2026)

1. Firebase project `kids-presents` on the Blaze plan, Firestore in `europe-west2` (London), Google sign-in on, web app registered (its config is in [`js/config.js`](js/config.js), with the web push key from Project settings › Cloud Messaging).
2. GitHub secret `FIREBASE_SERVICE_ACCOUNT`: the JSON from Project settings › Service accounts › Generate new private key. It's given the roles it needs in Cloud Shell:
   ```sh
   SA=$(gcloud iam service-accounts list --project kids-presents --filter="email~firebase-adminsdk" --format="value(email)")
   for r in firebasehosting.admin firebaserules.admin cloudfunctions.admin run.admin eventarc.admin cloudscheduler.admin iam.serviceAccountUser secretmanager.admin artifactregistry.admin serviceusage.serviceUsageConsumer datastore.indexAdmin; do
     gcloud projects add-iam-policy-binding kids-presents --member="serviceAccount:$SA" --role="roles/$r" --condition=None --quiet > /dev/null && echo "added $r"
   done
   ```
3. Google Calendar invites: turn on the Google Calendar API in Google Cloud, publish the OAuth consent screen (Google Auth Platform › Audience) so the connection doesn't expire after 7 days, put the Web client's ID in `js/config.js` and `functions/gcal.mjs`, and set its secret: `firebase functions:secrets:set GOOGLE_CLIENT_SECRET --project kids-presents`.
4. The Claude API key, as a functions secret: `firebase functions:secrets:set ANTHROPIC_API_KEY --project kids-presents`. It's pay-as-you-go from console.anthropic.com; reading an invite, asking for ideas or searching the shops costs a few pence each.

After that, everything deploys from GitHub on each push to `main`, by the `Test and deploy` workflow: the tests run first, and only if they pass are the site, the database rules and the functions published. It can also be run by hand from the Actions tab.

Worth doing once in Google Cloud: a budget alert (Billing › Budgets & alerts, say £5 a month), and daily database backups kept for a week, from Cloud Shell:

```sh
gcloud firestore backups schedules create --project=kids-presents --database='(default)' --recurrence=daily --retention=7d
```

## Run locally and test

```sh
npm install && npm --prefix functions install && node tools/copy-shared.mjs
npm test                                                  # unit tests: reminders, ages, idea matching, invites, friends, duplicates, calendar feed
firebase emulators:start --only auth,firestore             # Firestore on 8081, Auth on 9099
python3 -m http.server 8000                                # then open http://localhost:8000/?emulator
node test/e2e.mjs                                          # two people: a party, claiming and buying, an invite, real products and ideas (pretend Claude), the cupboard, a joint party, a duplicate invite, friends, reminders
```

With `?emulator` the sign-in page offers a test email sign-in, because Google sign-in needs Google's servers. The `Test and deploy` workflow runs both on every push and pull request. Screenshots from the end-to-end run land in `test/shots/`.

The app's code: [`js/app.js`](js/app.js) loads the screens in [`js/views/`](js/views) (one file each); [`js/core.js`](js/core.js) is the shell (routing, rendering, tap handlers), [`js/store.js`](js/store.js) the live data, [`js/events.js`](js/events.js) how parties look in lists, and [`js/gifts.js`](js/gifts.js) the rules shared with the functions. Every import carries the same `?v=` number; bump it everywhere (and in `index.html`) when the app changes. `vendor/firebase.js` is the Firebase SDK bundled from [`tools/firebase-entry.js`](tools/firebase-entry.js); the icons are made from `icon.svg` with `node tools/make-icons.cjs icon.svg icons`.
